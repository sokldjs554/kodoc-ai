# 서빙 벤치마크 실측 — FP16 vs AWQ (Tesla T4)

`benchmarks/bench_serving.py`로 직접 측정한 결과와 해석. 원본 JSON은
[`benchmarks/results/`](../benchmarks/results/)에 있고, 측정 환경이 각 파일의
`environment` 블록에 함께 기록돼 있다.

목적은 절대 성능 자랑이 아니라 **[추론 최적화 문서](inference-optimization.md)에
정리한 원리가 실제로 관측되는지** 확인하는 것이다. 그래서 측정 전에 가설을 먼저
적고, 맞은 것과 틀린 것을 그대로 남겼다.

## 측정 환경

| 항목 | 값 |
|---|---|
| GPU | Tesla T4 (15,360 MiB, 드라이버 580.159.04) — Kaggle 무료 노트북 |
| 엔진 | vLLM 0.26.0 / torch 2.11.0 / Python 3.12.13 |
| 모델 | `Qwen/Qwen2.5-3B-Instruct` (FP16) vs `Qwen/Qwen2.5-3B-Instruct-AWQ` (4bit) |
| 서버 플래그 | `--dtype float16 --max-model-len 4096 --gpu-memory-utilization 0.90` |
| 부하 | 요청 64개 × 동시성 {1, 4, 16, 64}, `max_tokens=256`, 한국어 프롬프트 8종 순환 |
| 실패 | 전 구간 0건 |

### 왜 7B가 아니라 3B인가

T4는 16GB라 7B FP16(약 15GB)이 한 장에 안 올라간다. T4 2장으로 tensor parallel을
쓸 수 있었지만 **쓰지 않았다.** Kaggle의 T4 2장은 NVLink 없이 PCIe로 붙어 있어
TP 통신 오버헤드가 측정값에 섞인다. 알고 싶은 것은 "양자화가 처리량에 주는 영향"인데
교란 변수를 하나 더 넣는 셈이다. 단일 GPU에서 모델 크기를 낮추는 쪽이 비교의 순도가
높다고 판단했다. 확인하려는 것이 절대 성능이 아니라 **곡선의 모양**이므로 모델 크기는
결론에 영향을 주지 않는다.

## 측정 전 가설

1. 동시성을 올리면 tok/s가 오르다 꺾인다. TTFT p95는 완만히 증가해야 한다 —
   계단식으로 튀면 배치 경계 대기가 있다는 뜻.
2. AWQ가 FP16보다 TPOT가 빠르다(decode는 대역폭 bound, 4bit는 읽을 바이트가 1/4).
   반대로 **배치 1의 TTFT는 AWQ가 불리**할 수 있다 — prefill은 연산 bound라
   역양자화 비용이 그냥 추가되므로.
3. AWQ가 더 높은 동시성까지 버틴다. 가중치가 줄어든 만큼 KV 캐시 풀이 커지므로.

## 해석 1 — decode가 메모리 대역폭에 묶여 있다는 것의 실측 증거

TPOT는 곧 **디코드 스텝 1회 시간**이다(스텝마다 배치 내 각 시퀀스가 토큰 1개씩 얻는다).
FP16에서 배치가 1 → 16으로 **16배** 늘어나는 동안 스텝 시간은 37.07 → 35.90ms로
**거의 변하지 않는데**, 처리량은 27.2 → 326.3 tok/s로 **12배**가 됐다.

스텝마다 가중치 전체를 HBM에서 읽어야 하고, 그 읽기 비용은 배치에 시퀀스가 1개든
16개든 동일하기 때문이다. 그래서 "가중치를 한 번 읽을 때 더 많은 토큰을 처리한다"
(= 배칭)가 거의 공짜인 구간이 생긴다.

수치로 확인:

| | 값 |
|---|---|
| T4 메모리 대역폭 (사양) | 320 GB/s |
| Qwen2.5-3B FP16 가중치 | 3.09B × 2B = 6.18 GB |
| 이론상 배치 1 디코드 상한 | 320 ÷ 6.18 = **51.8 tok/s** (19.3 ms/step) |
| 실측 배치 1 | **27.0 tok/s** (37.07 ms/step) |
| 대역폭 활용률 | **약 52%** |

이론치의 절반은 통상 범위다(커널 실행·스케줄러·활성값 트래픽이 나머지를 먹는다).
중요한 건 **측정값이 대역폭 상한과 같은 자릿수에서 움직인다**는 것 — 연산량으로는
설명되지 않는다.

**동시성 64에서 스텝 시간이 35.90 → 54.46ms로 뛴 지점이 배칭의 공짜 구간이 끝나는
곳이다.** 여기서부터 KV 캐시 읽기와 GEMM 연산이 무시할 수 없어진다. 처리량은 여전히
늘지만(4배 동시성에 3.1배) 효율은 떨어지고 있다.

TTFT p95는 79.8 → 98.4 → 149.2 → 382.5ms로 **완만하게** 증가했다. 계단식 도약이
없으므로 continuous batching이 정상 동작한다. → **가설 1 확인.**

## 해석 2 — 양자화 효과가 "읽은 바이트 수"에 비례했다

배치 1에서 TPOT가 37.07 → 12.76ms, **2.91배** 빨라졌다.

거꾸로 검산하면 더 분명하다. 대역폭 활용률이 FP16과 같다고 놓고 측정된 2.91배에서
역산하면 AWQ 가중치는 6.18 ÷ 2.91 = **약 2.13GB**가 나온다. 실제 AWQ 체크포인트
크기와 일치한다. 즉 **속도 향상이 읽어야 할 바이트 수에 거의 정확히 비례**했고,
역양자화 연산 비용은 이 구간에서 거의 드러나지 않았다. → **가설 2 전반부 확인.**

## 해석 3 — 가설이 틀린 곳: 짧은 프롬프트의 prefill도 대역폭 bound다

"배치 1의 TTFT는 AWQ가 불리할 수 있다"고 예상했지만 **전 구간에서 AWQ가 빨랐다**
(배치 1에서 45.4 → 34.7ms).

prefill이 연산 bound인 것은 **프롬프트가 충분히 길 때**다. 이 실험의 프롬프트는
한국어 20~40토큰 수준이라 연산량이 GPU를 채우지 못하는데, 그럼에도 가중치는 전부
한 번 읽어야 한다. 그래서 짧은 프롬프트의 prefill 역시 대역폭에 묶인다. 연산 bound로
넘어가는 경계는 프롬프트가 수백~수천 토큰일 때다.

RAG는 검색된 청크를 컨텍스트에 넣어 프롬프트가 길어지는 구조이므로, 실제 서비스의
작동점은 이 경계 반대편에 있을 가능성이 높다. **프롬프트 길이를 변수로 넣어 재측정하는
것이 이 실험의 가장 직접적인 후속 과제다.**

## 해석 4 — 양자화의 이득은 동시성이 오를수록 줄어든다

| 동시성 | TPOT 개선 | tok/s 개선 |
|---|---|---|
| 1 | **2.91배** | 2.85배 |
| 4 | 2.20배 | 2.22배 |
| 16 | 1.96배 | 1.66배 |
| 64 | **1.30배** | 1.31배 |

스텝 시간 증가폭을 보면 원인이 보인다.

| | 동시성 1 | 동시성 64 | 증가 |
|---|---|---|---|
| FP16 | 37.07 ms | 54.46 ms | +17.39 ms (+47%) |
| AWQ | 12.76 ms | 41.76 ms | +29.00 ms (+227%) |

가중치 읽기 비용은 배치와 **무관하게 고정**이고, KV 캐시 읽기와 GEMM은 배치에
**비례**한다. 배치가 커질수록 고정 비용의 비중이 작아지니, 그 고정 비용을 줄이는
양자화의 이득도 함께 작아진다.

절대 증가폭까지 AWQ가 더 큰 것(+29ms vs +17ms)은 여기에 더해, **역양자화 연산이
스텝이 연산 bound가 된 뒤에야 비용으로 드러나기** 때문으로 보인다. 배치 1에서는
메모리 대기 뒤에 숨지만, 배치 64에서는 그대로 노출된다. 이 부분은 추론이며 별도
프로파일링으로 확인하지 않았다.

**실무적 함의**: 양자화는 "무조건 빠르게 만드는 스위치"가 아니라 **저동시성 구간에
효과가 집중되는 최적화**다. 트래픽이 적은 서비스나 개인용 배포에서 이득이 크고,
GPU를 꽉 채워 돌리는 고부하 서비스에서는 기대 이득이 훨씬 작다. 추세를 연장하면
어느 배치 이상에서는 AWQ가 역전당할 것으로 예상되지만, **동시성 64까지는 여전히
AWQ가 앞섰다** — 역전 지점은 측정하지 않았다.

## 해석 5 — 가설 3은 검증하지 못했다

"AWQ가 더 높은 동시성까지 버틴다"는 KV 캐시 풀이 고갈되는 지점을 봐야 하는데,
이 실험의 시퀀스는 300토큰 안팎이라 동시성 64에서도 양쪽 모두 KV 여유가 충분했다
(실패 0건). 오히려 해석 4의 추세는 반대 방향을 가리킨다.

**미검증으로 남긴다.** 확인하려면 동시성 128/256 또는 긴 컨텍스트가 필요하다.

## 품질 — 속도만 재면 안 된다

같은 질문 3개를 `temperature=0`으로 양쪽에 물었다
([`quality_fp16.json`](../benchmarks/results/quality_fp16.json) /
[`quality_awq.json`](../benchmarks/results/quality_awq.json)).

| 질문 | FP16 | AWQ |
|---|---|---|
| 존댓말 변환 | `내일까지ご報告をいただけますと幸いです。` — **일본어 출력** | `"존버님, 내일까지 보고서를 제출해 주시기 바랍니다."` — 한국어는 맞으나 호칭 환각 |
| EC/pH 설명 | `EC(전기 Conductivity)` 영어 혼입 | `산碱性` **중국어 혼입**, 양액과 EC 혼동 |
| 온도 관리 | 무난 | `더 많은 꿀벌을 유발하거나` — 환각 |

새어 나온 언어가 다를 뿐(일본어 ↔ 중국어) **실패 유형은 같다.** 질문 3개를 한 번씩
뽑은 것이므로 "AWQ가 품질을 떨어뜨렸다"고 말할 수 없다. 말할 수 있는 것은 하나다 —
**3B 모델의 한국어 품질은 양자화 여부와 무관하게 서비스 수준에 못 미친다.**
[model-selection.md](model-selection.md)에서 7B를 고른 근거로 적었던 "동급 대비
한국어 품질"이 문헌 인용에서 실측 관찰로 바뀐 지점이다.

## 한계

- **모델이 3B다.** 위 사유로 선택했지만, 7B/14B에서 같은 곡선이 나온다는 보장은 없다.
  특히 해석 4의 역전 지점은 모델 크기에 따라 달라질 것이다.
- **프롬프트가 짧고 고정 길이대다.** 해석 3에서 드러났듯 이게 결과를 좌우한다.
- **동시성 간 종단 지연(latency) 비교는 유효하지 않다.** 요청 수가 64로 고정이라
  동시성 16은 4개 파도로, 64는 한 파도로 처리된다. 동시성 16의 p50/p95 격차가
  큰 것(9.31 / 17.53초)이 그 흔적이다. TTFT와 TPOT는 비교 가능하다.
- **TTFT에 클라이언트 큐 대기가 포함되지 않는다.** 하네스가 세마포어를 얻은 뒤
  타이머를 시작한다. 서버 측 TTFT이지 백로그 상황의 사용자 체감 TTFT가 아니다.
- **각 조건 1회 측정이다.** 분산을 모른다. TPOT가 동시성 1→4에서 살짝 내려간 것
  (37.07 → 31.40ms)은 측정 노이즈일 가능성이 있다.
- **대역폭 활용률 계산은 가중치 트래픽만 센 근사다.** KV 캐시·활성값 읽기를 빼고
  계산했으므로 실제 활용률은 52%보다 높다.

## 재현 방법

```bash
# 서버 (Kaggle 무료 T4 노트북에서 실행)
vllm serve Qwen/Qwen2.5-3B-Instruct \
  --dtype float16 --max-model-len 4096 --gpu-memory-utilization 0.90

# 측정
python benchmarks/bench_serving.py \
  --base-url http://localhost:8000/v1 --model Qwen/Qwen2.5-3B-Instruct \
  --num-requests 64 --concurrency 1 4 16 64 --max-tokens 256 --use-usage \
  --note "Tesla T4 x1, FP16, max-model-len 4096, gpu-util 0.90" \
  --output benchmarks/results/t4_fp16.json
```

AWQ는 모델명을 `-AWQ`로 바꾸고 `--quantization awq`를 추가하면 된다.
T4(Turing)는 bfloat16을 지원하지 않으므로 `--dtype float16`이 필수다.
(실행 시 `VLLM_USE_V1=0`을 설정했으나 vLLM 0.26에서 실제로 적용됐는지는 확인하지 않았다.)

## 다음 실험

- **프롬프트 길이 스윕** — 해석 3의 경계를 찾는다. 32/256/1024/4096 토큰에서
  AWQ의 TTFT 우위가 언제 사라지는지. RAG 작동점을 정하는 데 직접 필요한 데이터.
- **동시성 128/256** — 해석 4의 역전 지점과 가설 3(KV 풀 여유)을 동시에 확인.
- **`--max-model-len` 튜닝** — 4096 vs 2048로 KV 풀 크기를 바꿔 고동시성 처리량 변화 측정.
- **7B급 재측정** — 3B 결론이 실제 서비스 체급에서도 유지되는지.
