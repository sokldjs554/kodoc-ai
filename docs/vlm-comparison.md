# VLM 파싱 모델 비교 — 한국어 표 문서

파싱 단계에 어떤 VLM을 쓸지 고르려고 두 모델을 같은 입력으로 돌려 비교했다.
결과보다 **결과의 해석**이 이 문서의 목적이다: 파싱 오류가 하류 검색에서
어떤 모양으로 터지는지가 모델 선정 기준을 바꾼다.

## 실험 설정

| 항목 | 값 |
|---|---|
| 입력 | 한국어 표 1개 (4행 3열, 전문용어 + 영문 약어 + 화살표 기호 혼재) |
| 정답 | [`benchmarks/README.md`](../benchmarks/README.md) 의 "측정 지표" 표 원문 |
| 비교 대상 | `claude-haiku-4-5` / `claude-sonnet-5` |
| 호출 경로 | `VLMDocParser` → OpenAI 호환 API (`kodoc.service.deps.build_vlm_parser`) |
| 프롬프트 | `VLM_PARSE_PROMPT` (양쪽 동일) |
| 실행 횟수 | 각 1회 |

정답을 저장소 안 문서로 잡은 것은 의도적이다. 실제 스캔 문서에는 정답이 없어서
파싱 품질을 수치화할 수 없다. 이미 텍스트로 존재하는 표를 렌더링해 캡처하면
**바이트 단위 대조가 가능한 정답이 생긴다.**

입력과 출력 원본은 모두 저장소에 있다:

| 파일 | 내용 |
|---|---|
| [`data/samples/parsed/scan.png`](../data/samples/parsed/scan.png) | 입력 이미지 (위 표를 화면에 띄워 캡처) |
| [`data/samples/parsed/scan_haiku45.md`](../data/samples/parsed/scan_haiku45.md) | `claude-haiku-4-5` 출력 |
| [`data/samples/parsed/scan_sonnet5.md`](../data/samples/parsed/scan_sonnet5.md) | `claude-sonnet-5` 출력 |

`diff benchmarks/README.md의 해당 6줄 data/samples/parsed/scan_sonnet5.md` 가
차이를 내지 않는 것으로 "완전 일치"를 확인했다.

## 결과

`claude-sonnet-5` 출력은 원문과 **바이트 단위로 동일**했다(`diff` 결과 없음).
`claude-haiku-4-5`는 아래 차이를 냈다.

| 위치 | 원문 | haiku-4-5 | sonnet-5 |
|---|---|---|---|
| TTFT 행 | 큐 대기의 **함수** | 큐 대기의 **합수** | 일치 |
| TPOT 행 | decode 성능의 **함수** | decode 성능의 **합수** | 일치 |
| TPOT 행 | 스트리밍 **타이핑** 속도 | 스트리밍 **타이밍** 속도 | 일치 |
| tok/s 행 | 감당 가능한 **동시** 사용자 | 감당 가능한 **토시** 사용자 | 일치 |
| 문장 부호 | `.` | `,` (3곳) | 일치 |
| 표 밖 | 없음 | `# 지표별 의미 및 왜 중요한가` 제목 생성 | 없음 |

문자 오독 4건, 부호 4건, 원문에 없는 제목 1줄. 표 구조(행·열 경계, 셀 병합 없음,
`→` 기호)는 두 모델 모두 정확히 복원했다.

## 해석 — 파싱 오류는 검색에서 무음으로 터진다

haiku의 오류가 전부 **한글 자모 수준의 조용한 치환**이라는 점이 중요하다.
`함수→합수`, `동시→토시`, `타이핑→타이밍`. 문장이 여전히 그럴듯하게 읽혀서
눈으로 훑는 검수로는 잘 안 걸린다.

이게 RAG에 들어가면 검색에서 드러난다. 색인에 `합수`가 들어간 상태에서
사용자가 "decode 성능의 함수"를 물으면 BM25는 이 청크를 못 찾는다.
Kiwi로 조사·어미를 아무리 잘 떼어내도 **원문 토큰 자체가 틀렸으면 복구가 안 된다.**
dense 검색이 일부 건져낼 수는 있지만, 그건 우회지 해결이 아니다.

정리하면 파싱 정확도는 독립적인 품질 지표가 아니라 **하류 검색 성능의 상한**이다.
그래서 모델 선정 기준이 이렇게 바뀐다:

- 저렴한 모델을 쓰려면 파싱 결과 **검증 단계가 전제**가 된다 — 원문 대조가
  가능하면 대조, 아니면 사전·형태소 기반 비어(非語) 탐지. `합수`, `토시`는
  분석기에서 미등록어로 걸러낼 수 있는 종류의 오류다.
- 그 검증 비용을 감안하면 **파싱 단계만큼은 상위 모델이 오히려 싸질 수 있다.**
  파싱은 문서당 1회지만 검색은 질의마다 반복되므로, 색인 품질에 드는 비용은
  한 번 지불하고 계속 회수하는 쪽에 가깝다.

## 이 실험에서 딸려 나온 것

같은 코드로 모델만 바꾸다가 `claude-sonnet-5`가 `temperature`를 받으면
400을 돌려준다는 걸 발견했다. "OpenAI 호환"이 지원 파라미터까지 같다는 뜻은
아니라는 것 — 자세한 내용과 대응은 [ARCHITECTURE.md](ARCHITECTURE.md)의
"호환의 한계" 항목에 적었다.

## 한계

이 결과를 일반화하면 안 되는 이유를 명시해 둔다.

- **표본 1건.** 이미지 1장, 각 모델 1회 실행이다. 통계가 아니라 관찰이다.
  모델 간 차이를 주장하려면 최소한 문서 유형별로 수십 건은 필요하다.
- **조건이 완전히 통제되지 않았다.** haiku는 `temperature=0.0`으로, sonnet은
  파라미터를 받지 않아 생략한 채로 돌렸다. 위에서 언급한 400 이슈 때문이다.
  같은 조건에서의 재측정이 필요하다.
- **입력이 스캔이 아니다.** 화면 캡처라 해상도·기울기·노이즈가 없다. 실제
  스캔 문서에서는 두 모델의 격차가 이보다 커질 가능성이 높다.
- **비용·지연을 측정하지 않았다.** 실제 선정에는 품질만이 아니라 문서당
  단가와 파싱 지연이 함께 들어가야 한다.

## 다음 단계

- 정답이 있는 파싱 평가셋 구성 — 저장소 내 마크다운 문서들을 렌더링·캡처해
  입력을 만들면, 정답 대조가 자동화된다. 문자 단위 정확도(CER)와 표 구조
  일치율을 분리 측정.
- 형태소 분석기 기반 파싱 검증기 — 미등록어 비율이 임계치를 넘으면 상위 모델로
  재파싱하는 계단식(cascade) 구성. 위 "저렴한 모델 + 검증" 안의 구현.
- 오픈 모델(Qwen2.5-VL-7B) 포함 3자 비교 — 자체 GPU 서빙 시의 품질·비용 위치 확인.
